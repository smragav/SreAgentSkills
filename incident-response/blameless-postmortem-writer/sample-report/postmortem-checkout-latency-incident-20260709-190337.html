Summary

For 46 minutes, the checkout API returned timeouts for a share of users after a configuration change reduced the database connection pool. Rolling the change back restored service.

Root cause

A configuration change lowered the connection pool ceiling well below steady state demand (trigger). No guardrail validated pool size against expected concurrency before apply (weakness).

Contributing factors

  • No saturation alert on connection pool usage
  • The appsettings change bypassed the usual review because it was flagged as a minor tweak
  • Runbooks did not list pool size as a high blast radius setting

Detection

An Azure Monitor latency alert on p95 fired five minutes after the breach.

Resolution

The on-call restored maxPoolSize to 100. Latency recovered within four minutes and the incident was resolved.

Lessons

What went well

  • The latency alert caught the breach quickly
  • Rollback was a single, well understood step

What went wrong

  • No guardrail on the pool size change
  • Pool saturation was not directly alerted

Where we got lucky

  • Traffic was below peak, so the blast radius stayed at roughly 12%
